# 難查的 bug：先做出「會變紅的迴路」，沒有迴路不准提假說

## 會這樣問

- 這個 bug 找不到原因怎麼辦？
- 難查的 bug 要從哪裡下手？
- 偶發性的問題怎麼 debug？
- 效能突然變差要怎麼查？
- 我一直在猜原因，猜不到怎麼辦？

## 一句話

**debug 的技術含量全在「建立一個對這隻 bug 會變紅的快速迴路」，其餘（二分搜尋、驗假說、加探針）都只是在消費那個迴路。**

## 做法／判準

**Phase 1 建迴路（這一步就是整套技藝，值得不成比例地投入）**。建法由易到難：
失敗測試 → curl／HTTP 腳本 → CLI 餵 fixture 比對輸出 → headless browser → **重放錄下來的 trace**
→ 拋棄式 harness（只起最小子系統）→ property/fuzz 跑一千次 → 二分搜尋 harness → 差分（新舊版同輸入比對）
→ 最後才是「人要點按鈕」的半自動腳本。

**完成判準（可判定，不是感覺）**：你能講出**一條指令**，而且**已經至少跑過一次**（貼出呼叫與輸出），並滿足：
- **會變紅** —— 走的是真正的 bug 路徑、斷言的是**使用者描述的那個症狀**（不是「沒炸就算過」）
- **決定性** —— 每次結論一樣（偶發 bug 則是把重現率拉高到可 debug）
- **快** —— 秒級不是分鐘級
- **agent 自己跑得動**

⛔ **「還沒有那條指令就開始讀 code 湊理論」＝ 這套流程專門要擋掉的失敗。** 沒有紅燈就沒有 Phase 2。

**迴路要當產品磨**：更快（快取 setup、砍無關初始化）、訊號更利（斷言具體症狀）、更決定性
（釘時間、固定亂數種子、隔離檔案系統與網路）。**30 秒又會飄的迴路幾乎等於沒有；2 秒決定性的迴路是超能力。**

**偶發 bug 的目標不是乾淨重現，是提高重現率** —— 迴圈跑 100 次、加壓、注入 sleep 縮時間窗。
50% 可 debug，1% 不行，先把率拉上來。

**真的建不出來就明說**，列出試過什麼，然後跟人要：能重現的環境／去敏感化的現場產物（HAR、log dump、錄影）／
加暫時性生產探針的許可。**不准跳過迴路直接開始假設。**

Phase 2：跑迴路看它變紅 → 確認紅的是**使用者說的那個症狀**（紅錯 bug ＝ 修錯東西）→
**縮到最小仍會紅的情境**（一次砍一項、每砍一次重跑）。
