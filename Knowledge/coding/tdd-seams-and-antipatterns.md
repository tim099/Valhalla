# 測試要寫在哪、什麼是壞測試（seam 與三種反模式）

## 會這樣問

- 測試應該測到什麼程度？
- 這個東西要怎麼寫測試？
- 為什麼我一重構測試就全紅？
- 測試該放在哪一層？
- 要先把測試全部寫完再實作嗎？

## 一句話

**測試寫在「事先講好的公開介面（seam）」上，一次一片垂直切片；一重構就紅的測試不是嚴謹，是耦合到實作。**

## 做法／判準

**好測試的形狀**：透過公開介面驗**行為**，讀起來像規格（「使用者可以用有效購物車結帳」）。
實作整個換掉，測試不該動。

**seam ＝ 你觀察行為而不必伸手進去的那個介面。**
⭐ **只在事先講好的 seam 上測** —— 動筆前先寫下要測哪些 seam 並跟人確認。
不可能什麼都測，**事先議定 seam 就是讓測試力氣落在關鍵路徑與複雜邏輯上**的手段。

**三種反模式**：
- **耦合實作** —— mock 內部協作者、測私有方法、從側門驗（直接查資料庫而不走介面）。
  **判別法：行為沒變、重構就紅。**
- **同義反覆** —— 斷言用跟實作同一套算法把預期值再算一次（`expect(add(a,b)).toBe(a+b)`、
  手工照同樣邏輯推出來的 snapshot）。它**先天必過**，永遠不可能跟 code 唱反調。
  ⇒ 預期值要來自**獨立的真相源**：已知good的字面值、手算範例、規格。
- **橫向切片** —— 先把測試全寫完再全部實作。那樣測到的是**想像中的行為**：測到形狀而非使用者行為，
  對真實變更變得不敏感，而且在理解實作之前就把測試結構定死了。
  ⇒ 改成**垂直切片**：一測試 → 一實作 → 再一輪，每個測試都是一發曳光彈，回應上一輪學到的東西。

**迴路規矩**：紅先於綠（先寫失敗測試，再寫剛好夠讓它綠的 code，不預先寫將來才要的功能）／
一次一片（一 seam、一測試、一最小實作）／**重構不屬於紅綠迴路**，那是 review 階段的事。
