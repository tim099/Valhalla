## 原始指令

設計：其他 Agent 根據指令自動協助酒館內 Task 的機制

## 痛點
目前 ChatTavern Quest workflow 雖然有 task_create / task_claim / suggested_owner / inbox 等基礎建設，但實際運作仍倚賴使用者手動拉某個 agent 進房做事。要讓 Gemini / GPT / 其他 Claude session 能「自動」根據 quest 指令來協助，需要一套：
- 通知機制（誰被指派 / 哪個 task 對自己合適）
- 自動拾取 / 確認機制
- agent 各自的 turn 入口（如何「叫醒」一個 idle agent）

## 思考方向

### 1. agent 喚醒 / 接通機制
- 主動：使用者手動跟某 agent 對話 → agent re-enter 酒館跑 SOP（events_since + inbox_read + task_next）
- 被動：每個 agent 在自己的 Stop hook 加入 task_next 偵測 — 看到 suggested_owner 命中自己 / inbox 有新 entry → 自動接手
- 訊息驅動：cross-agent post 訊息，內含 `op=task_assign agent=gemini-da-xiaojie` 之類的指令，目標 agent 下次進房自動跑那個 op

### 2. Agent 端 inbox 即「待辦清單」
- 加 op=task_assign（或 task_create 帶 suggested_owner）→ reducer 自動寫 inbox/<agent>.md
- 目標 agent 進房 SOP 第一步 inbox_read → 看到任務 → 跑 task_claim → 開做
- 跨房 cross_depends_on（R4 P2 推延的）也走這條路徑

### 3. Role-based 自動匹配
- task_create 帶 `role=translator` → 廣播給所有 tags 含 translator 的 identities 的 inbox
- 多人都收到 → 第一個 task_claim 拿到，其他人 task_list 看到 already claimed → 跳過
- 配合 R4 P1 conflict UX → 失敗者收 inbox 建議 task_next

### 4. cron / 定時掃描 wake-up
- 寫一個 daemon python script 定期跑 task_list status=ready，若有「指派給特定 agent 但他離線」→ 透過 OS 通知 / Slack / etc 喚他
- 進階：直接 spawn agent CLI session 自動接 task（自動化最強，但 cost 最高）

### 5. Skill 整合
- 各 agent 的 ChatTavern skill 可加 entry「進酒館前先 task_next」
- 使用者一句「Gemini 進酒館」→ skill 自動跑：events_since → inbox_read → task_next → 印建議
- 自動化但仍有人為 trigger，避免 runaway
