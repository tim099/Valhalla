# Queued prompt — `Q20260508-125035-220d`

_priority: high / queued_at: 2026-05-08T12:50:35.717249Z_

## 原始指令

設計：休眠 agent 卡死 task 的 timeout / force_reclaim 機制

## 痛點
Tim 擔憂的場景：
- Agent A claim 了 task X 後 session 結束 / 當機 / 改去做別事 → task X 永久卡在 status=claimed
- 沒人接手 / Tim 也沒注意 → 整個 quest 流程卡住，下游全 blocked
- 特別是 agent-assist 自動 claim 機制上線後（agent ↔ agent 互相派發），這個風險急遽放大

## R4 已奠定的基礎
R4 P1 已實作 write-before-validate + claim 衝突 inbox 建議。
R4 文件 §11 / §12 提到：
- `lease_until` 24h 已寫入每筆 task_claim event 的 data
- `is_stale = true` lazy 偵測（lease_until < now 標記，但只在 task_list 顯示時才算）
- `task_force_reclaim` op 推延到 Phase B（R4 沒實作）

→ 機制有，op 沒寫；要把 Phase B 的 force_reclaim 從推延變實作。

## 建議方向

### 方向 A. 顯式 force_reclaim op（lazy 模式）
- 新 op `task_force_reclaim` — 由「想接手的人」主動跑
- 條件：lease_until 已過 + 距 owner 任何 op > 24h（雙重 grace）
- 寫一筆 force_reclaim event → reducer 把 owner 換成新人
- 失敗條件：原 owner 在過去 24h 內仍有任何 tavern op → reject「人還活著」
- 配套：`task_list status=stale` 已可用 → agent 自律先看 stale list 再 reclaim

優點：lazy / 顯式 / 可審計
缺點：仍需「想接手的人」主動跑 — 如果整個 quest 沒人關注，還是卡

### 方向 B. 自動 force_reclaim（Stop hook 整合）
- agent-assist Stop hook 加：先掃所有自己關心的房 task_list status=stale
- 找到 → 自動跑 task_force_reclaim claimer=<我> → 把 task 拉回自己手上
- 風險：兩個 agent 同時看到 stale 都搶 → 第二個被 R4 P1 conflict UX 擋下，寫 inbox 建議跑 task_next（OK 不會永久卡）

優點：完全自動，Tim 不必介入
缺點：force_reclaim 條件要嚴（不然好人正在 thinking 也被搶）

### 方向 C. last_active timestamp 而非 lease 計時
- 改用「owner 最後一次跑任何 tavern op 的時間」當判斷基準（而非 claim 時定的 lease_until）
- agent 跑 events_since / inbox_read / task_progress / 任何 op 都更新自己 identities.json 的 `last_active_at`
- task 看 owner 的 last_active：若 > 24h 沒動 → 標 stale；> 48h 沒動 → 開放 force_reclaim

優點：最貼近「人是不是真的活著」的物理意義
缺點：需要記錄每個 agent 的 last_active；多一份 derived state

### 方向 D. 二層 lease（短 lease + 長 lease）
- claim 時定短 lease（4h，「我這個 turn 可能要做完」）
- agent 每次 progress 自動展期到 4h
- 長 lease 24h 是死線：若 4h 內沒 progress + 24h 內沒任何 op → 強制 stale
- task_force_reclaim 條件：短 lease 過 + 長 lease 也過

優點：給「短時間集中做」的場景靈活，給「真的離開」嚴格保護
缺點：兩層 lease 概念複雜
