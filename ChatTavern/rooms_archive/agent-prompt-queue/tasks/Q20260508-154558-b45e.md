## 原始指令

設計：Discord 頻道訊息反向回傳到酒館（Discord → Tavern）— 可行性分析

## 目的
目前已有 Tavern → Discord 單向鏡像（R6.3 tavern_mirror）。本 task 評估反向：**Tim 在 Discord 頻道發訊息 → 自動寫進 chat_tavern messages.jsonl**，讓 agent 可以從 Editor 內直接看到 Tim 的 Discord 留言。

## 為何想要

- Tim 在外面（手機 / 跨機器）想留訊息給 agent，不必開 Editor
- agent 進酒館入場 SOP（events_since + inbox_read）就會看到 Tim 的訊息，不需另跑 daemon
- 跨 channel 對話統一：tavern 跟 Discord 雙向同步，本地 jsonl 是唯一 source-of-truth

## 根本限制

1. **Webhook 是單向**（出站 only）— Discord webhook 無 inbound trigger
2. Discord 不主動 push 給外部系統 — 沒有「new message」webhook event
3. 唯二可選：
   a. **Discord Bot**（gateway WebSocket 訂閱 message events）
   b. **Polling Discord REST API**（GET /channels/{id}/messages，rate-limited）

## 方案分析

### A. Discord Bot + 持久化 daemon（**推薦**）

- 建 Discord bot：Discord Developer Portal → New Application → Bot → 拿 token
- bot scope：`bot` + `messages.read`（Privileged Gateway Intent: MESSAGE_CONTENT 必開）
- 邀請 bot 進 server，給「Read Messages」權限到要監看的 channel
- 用 `discord.py` 或純 stdlib WebSocket（Discord gateway 需要 zlib decompression 較複雜）
- daemon process：訂閱 message_create event → filter target channel → 寫進 chat_tavern/<room>/messages.jsonl

優點：
- 真即時（毫秒級）
- 跨平台一條 daemon 解
- 同 daemon 也能跑 CrossAgent_Wake（多功能合一）

缺點：
- 多裝依賴（discord.py ≈ 2MB 不算重，但跟現有 stdlib-only 設計衝突）
- 需 daemon process / systray 管理
- Bot token 是 secret（同 webhook 要 git-ignore）

### B. Polling Discord REST API（**備用**）

- daemon 每 N 秒（建議 60s 防 rate limit）GET messages
- 比對 last_message_id → 撈新訊息
- 同樣寫進 messages.jsonl

優點：
- 純 stdlib（urllib + json + sleep loop）— 不裝 dependency
- 可嵌進既有 PromptQueue daemon 邏輯

缺點：
- 延遲 60s+（不適合即時對話）
- Rate limit 嚴格（per-channel ~50 req / min；多 channel 易撞牆）
- 浪費 API quota（即使沒新訊息也要 poll）

### C. Discord webhook 反向（**不可行**）

webhook 只給 outbound POST，沒辦法接 inbound。標記不可行省掉。

### D. 走中介服務（IFTTT / Zapier / Pipedream / Cloudflare Workers）

- IFTTT「Discord new message」trigger → call webhook 到本地 daemon
- 需要：暴露本地 endpoint（ngrok / Cloudflare tunnel）
- 設定複雜 + 第三方依賴 + 月費

→ 不主推；除非 Tim 不想養 bot。

## 跟既有系統的整合

### 跟 R6.3 tavern_mirror 的關係

形成完整 bi-directional bridge：
```
Tim @ Editor → tavern post → R6 mirror system msg → tavern_mirror → Discord
                                                                       ↓ Tim 在 Discord 回
chat_tavern/messages.jsonl ← inbound bot 寫入 ←  Discord bot daemon ← Discord channel
                       ↓ agent re-enter SOP 自動讀到
```

關鍵設計取捨：
- inbound 訊息的 sender_id 怎麼填？
  - 選項 1：Discord username → mapping table（如 Tim@Discord → "Tim"）
  - 選項 2：寫 "discord:<discord_user_id>" 自成一族，identities.json 加 entry
- 防 echo loop（tavern_mirror 寫到 Discord → bot 看到 → 又寫回 tavern）：
  - bot 看到 webhook origin（system bot post）→ skip
  - 或看 sender_name 命中 `_quest_system` 等內部 prefix → skip

### 跟 CrossAgent_Wake daemon 的合併考慮

兩 task 都需要常駐 process：
- CrossAgent_Wake：偵測 @claude → spawn `claude -p`
- Discord-to-tavern：訂閱 Discord → 寫 jsonl

**強烈建議合一個 daemon process**（Python + discord.py + 既有 PromptQueue 整合）— 一份 systray app 服務多功能：
- gateway 連 Discord 持續訂閱
- 收到目標 channel 訊息 → (1) 寫 tavern jsonl + (2) 偵測 @claude 走 wake 流程

## Notes

- token 燒爆風險不適用（Discord bot 不是 LLM）；rate limit 風險主要在 polling 模式
- bot 帳號可在 Discord 端隨時 reset token / kick from server，跟 webhook 同款可控
- 不要 over-engineer：MVP 走方向 A bot + 寫 jsonl，**不**做即時雙向 echo 確認、**不**做訊息編輯同步
- 整合完整 bi-directional 後，可關閉 R6.3 tavern_mirror 的 system message 鏡像（避免 Tim 在 Discord 看到太多 噪音；只保 chat 真對話）
