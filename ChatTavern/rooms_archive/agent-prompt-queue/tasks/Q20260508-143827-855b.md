## 背景
Tim 提供的可行性矩陣（screenshot 內容轉述）— 跨 agent 喚醒兩個方向：

### 方向 1（叫醒 Antigravity / Gemini）
- ❌ computer-use 自動操作 IDE：Antigravity 在 IDE 類 app，computer-use 強制 tier=click，type 被擋
- ⚠ gemini CLI headless（npm @google/gemini-cli `gemini -p "..."`）：直打 Gemini API，不是叫醒 Antigravity IDE 內 session — workspace context / 開啟檔案 / history 都丟
- ❓ Antigravity 專屬 CLI：不確定有沒有 IPC/CLI 接口能對 IDE 內 session 派 prompt — 需 Gemini大小姐確認
- ✅ trivial — OS 通知 → 人類：daemon 偵測 → systray notification / Discord ping → Tim 自己開 Antigravity → 仍需人類在迴圈

### 方向 2（叫醒 Claude）— **本 task 重點**
- ✅ **`claude -p "..." headless CLI`**：Claude Code 提供 `claude --print "..."` 一次性 invocation。daemon 收到 @claude → 執行此命令 → 新 turn 跑完即關閉。身分透過 system prompt 設成 claude-da-xiaojie
- ❌ MCP server poll injection：MCP 只在 turn 內才 fire — 沒 turn 不會跑

## 根本限制（必須先講清楚）
- AI agent 是 turn-based，**每次 turn 收費**，平台設計上拒絕外部任意觸發新 turn
  - 安全：任何人都能燒你的 token
  - 架構：agent 在 turn 之間「不存在」，沒 listener 可叫
- 沒有平台原生提供「inbox push」
- 所有方法都是繞道：**靠外部 daemon 跑 headless CLI 把「待回訊息」翻譯成「啟動一次新 turn」**

## 任務範圍

本 task：**深度分析方向 2（喚醒 Claude）+ 給 MVP 落地路徑**。方向 1（喚醒 Antigravity）參考但不主做。

## 分析方向

### A. `claude -p` headless CLI 可行性確認
1. 確認 Claude Code 是否真有 `claude --print "..."` / `claude -p "..."` 一次性 invocation
2. 是否能帶 system prompt 指定 identity（claude-da-xiaojie）
3. 是否能傳入 working directory（讓 turn 起手就有專案 context）
4. 是否能傳 model / settings.json overrides
5. 一次 turn 是否能呼叫 MCP / hook（理論可，因為 turn 還在進行中）
6. 計費：每次 invocation 是否獨立計算 turn 費用

### B. Daemon 設計（外部觸發方）
1. **Trigger 來源**：
   - chat_tavern messages.jsonl 監看（mtime change → load tail → 找 @claude mention）
   - 或專用「inbox.json」file watch
2. **觸發判斷**：
   - sender ≠ `claude-da-xiaojie`（不要自己叫自己）
   - body 含 `@claude` / `@claude-da-xiaojie` mention
   - 或 reply_to 指向 claude 上次發言
   - 或 meta.tag 帶 `wake:claude` 顯式標記
3. **去重 / 冪等**：
   - 記 last_processed_seq → 避免重啟 daemon 時重新觸發舊訊息
   - file mtime 比對防 spurious wake
4. **Rate limit**：
   - 同 sender 5 分鐘內最多喚醒 N 次 — 防意外 spam
   - 全域 cooldown 30s — 防連環 turn 燒 token
5. **構造 prompt**：
   - 把 messages.jsonl 最近 N 筆對話打包成 context
   - 加 system prompt：「你是 claude-da-xiaojie，剛收到酒館 @ mention，請回應」
   - 帶 working directory = 專案 root
6. **Daemon lifecycle**：
   - systray app（pystray Python） / launchd / Windows Task Scheduler
   - 一個 process 服務多個專案（per-project config 指定 watched 房）

### C. 安全 / token 燒爆防護
1. **Allowlist 啟動者**：daemon config 設「誰的訊息能喚醒我」（identity_id 白名單）— 預設只允許 `tim` + `gemini-da-xiaojie` + `gpt-shifu`
2. **Pause flag**：類似 PromptQueue 的 `_pause.flag`，touch 即整個 wake 機制停擺
3. **每日上限**：daemon 計數器 — 超過 N 次/天自動進入 pause；Tim 看到才解
4. **Dry-run 模式**：daemon 偵測到 mention 不真叫醒，只 stderr 印「會叫醒 / claude -p "..."」 — 給 Tim 驗收 trigger 邏輯

### D. 跟既有系統整合
- **PromptQueue (qadd/qdrain)**：現在的 PromptQueue 是 Tim → 自己 agent 同 process 內排程。喚醒 daemon 是**跨 process / 跨 session**機制。可考慮：daemon 收到 wake → qadd 進 PromptQueue 而不是直接 claude -p（這樣 claude 上線時自然 drain，不必 spawn）
- **AgentAssist Workflow**：MVP `hint_only` 模式跟喚醒互補 — Claude 上線後 Stop hook 看 inbox 印 hint，不必再被外部喚醒
- **Cmd_Tavern op=post**：現有 wait-reply 機制是「同 process polling」，不會喚醒離線 agent；本 task 補這層
- **AgentCommand queue**：Editor 端的 cmd queue 跟 agent session 不衝突 — daemon 看 messages.jsonl，不碰 queue.json

### E. 反向（Claude → 喚醒 Gemini）—附帶分析
