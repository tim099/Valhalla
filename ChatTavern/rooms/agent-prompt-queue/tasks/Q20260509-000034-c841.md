## 議題

T08 結論「per-channel 一對一」確認了路由方向，本 task 補設計細節：

**Tim 的想法**：用一組獨立 Webhook 作為「指令輸入頻道」。
- 每個 input webhook 對應一個本地酒館房（例：webhook A → tavern, webhook B → chat-flow-robust）
- 該 channel 的消息只要 **未讀過** 就透過某種方式通知 Agent 接收

關鍵突破點：**Webhook URL 不只是 outbound 推送 endpoint，也是 channel pointer**。Discord webhook GET API 可從 webhook URL 解出 channel_id；之後 bot 用 channel_id 訂閱該 channel 的 message_create event。

→ Tim 不必告訴 daemon 一堆 channel ID，只需要設一組 webhook（已熟悉的 UI 流程），daemon 自己從 webhook 解 channel。

## 研究 / 設計問題

### 1. Webhook → Channel 解析
- Discord API: `GET /webhooks/{id}/{token}` 回 webhook info 含 `channel_id`
- 之後 bot 用 channel_id 訂閱（不需要 token，只需要 channel_id）
- 實作：daemon 啟動時對每個 input webhook URL 跑一次 GET 拿 channel_id 寫進 mapping table

### 2. 「未讀」追蹤
- 每個 input channel 維持 `last_read_message_id`（per channel state）
- bot 連線時補抓 last_read 之後的所有訊息
- 推進策略：
  (a) 寫進 tavern jsonl 後立刻推進（最簡）
  (b) 等 agent 真的讀過 inbox 才推進（複雜，需 ack 機制）
  → 推 (a) — agent 自己負責讀 inbox / messages.jsonl，daemon 只負責「進貨」

### 3. 通知 Agent 的 wake 方式（跟 T09 結論銜接）
- 寫 jsonl + R7 mention parser → 自動進對方 inbox
- 同時：notify_discord wake-notify stream（T09 推薦）broadcast 一條 ping「@<agent> inbox 有 N 筆未讀」
- agent 上線跑 inbox_read 看到 → 直接接

### 4. 跟既有 outbound config 的對偶
`notify_config.json.tavern_mirror` 已有 webhook + rooms list（outbound）；新加 `tavern_inbound` section 對偶：
```json
{
  "tavern_inbound": {
    "enabled": false,
    "webhook_urls": [   // 每個 webhook 對應一個 channel
      "https://discord.com/api/webhooks/.../tokenA",
      "https://discord.com/api/webhooks/.../tokenB"
    ],
    "channel_mappings": [  // daemon 啟動時自動 fill 從 webhook 解出 channel_id
      { "channel_id": "...", "tavern_room": "tavern" },
      { "channel_id": "...", "tavern_room": "chat-flow-robust" }
    ],
    "sender_user_mappings": { "<discord_user_id>": "Tim" },
    "last_read_state": { "<channel_id>": "<message_id>" }
  }
}
```
