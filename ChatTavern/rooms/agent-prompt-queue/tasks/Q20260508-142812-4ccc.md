## 原始指令

Quest workflow 優化：task lifecycle 自動鏡像到聊天室

## 痛點
目前 Quest workflow 的 task lifecycle (claim / progress / done / release / force_reclaim / etc.) 只寫進 events.jsonl + inbox。**對話房本身沒看到 task 起手 / 完成的訊號**，agent 與人都要去查 task_state / task_list 才知道進度。

結果：
- 互動感弱 — 像在跟空氣協作，看不到「夥伴正在動 / 完成了」
- 工作紀錄分裂 — chat history（messages.jsonl）跟 task history（events.jsonl）兩條線各自獨立
- agent 在腦力激盪到一半開了 task → 但沒人看到他開了，下一輪別人 brainstorm 還沿著舊路徑
- 視覺斷層 — task_state 是事後看 timeline，缺了「即時感」

## 目標
**每筆關鍵 task event 同步寫一筆聊天室訊息**（當前 quest 房 messages.jsonl）作為 system message，讓對話流自然看到 task 進度。

## 設計方向

### 1. 哪些 event 要鏡像？

每筆事件對「值不值得鏡像」打分（避免 over-noise）：

| Event type | 鏡像？ | 訊息範本 |
|---|---|---|
| `task_create` | ✅ | `🆕 {actor} 建任務 \`{task_id}\` — {title}（priority={priority}）` |
| `task_claim` | ✅ | `🔒 {actor} 認領 \`{task_id}\`（lease until {lease_until}）` |
| `task_progress` | 🟡 視內容 | 有 summary 才鏡像；空 summary 跳過 |
| `task_review_request` | ✅ | `🔍 {actor} 提交 \`{task_id}\` 給審查` |
| `task_done` | ✅ | `✅ {actor} 完成 \`{task_id}\` — {title}` |
| `task_reject` | ✅ | `↩ {actor} 退回 \`{task_id}\` — {reason}` |
| `task_reopen` | ✅ | `♻ {actor} 重開 \`{task_id}\` — {reason}` |
| `task_release` | ✅ | `🛗 {actor} 放棄 \`{task_id}\` — {reason}` |
| `task_force_reclaim` | ✅ | `⚡ {claimer} 接管 \`{task_id}\`（原 owner: {previous_owner}，原因：{reason}）` |

**不鏡像**：純查詢 op (task_list / task_next / task_state / events_since / inbox_read) — 沒事件變動

### 2. 訊息應該長怎樣

走既有 messages.jsonl schema 的 `kind=system`（已有定義；現在 join/leave 走 system，task 鏡像同款）：

```jsonl
{"seq":42,"ts":"...","sender_id":"_quest_system","sender_name":"Quest","kind":"system","body":"🔒 claude-da-xiaojie 認領 `T01-schema` (lease until 2026-05-09T...)","meta":{"event_type":"task_claim","task_id":"T01-schema","event_seq":12}}
```

`meta.event_seq` 反指 events.jsonl 的對應筆，雙向 trace 通暢。
`sender_id=_quest_system` 用底線開頭區分系統訊息（不會跟真實 agent 撞）。

### 3. 實作位置

最自然的接入點：[`UCL_ChatTavernQuestIO.AppendEvent`](../../CardGame/Assets/UCL/UCL_Core/UCL_Core_Scripts/EditorCore/UCL_AgentCommands/ChatTavern/UCL_ChatTavernQuestIO.cs)

- AppendEvent 在 reducer 寫入 events.jsonl 時 trigger
- 同位置補一個 `MirrorEventToChat(roomId, event, taskState)` helper
- 用 `UCL_ChatTavernIO.AppendMessage` (假設既有的 chat append API；要查) 寫 system message
- 從 reducer 算出當下 task title 等資訊填入訊息

### 4. 開關 / 控制

- **預設 on**（要的就是互動感）
- room 級 opt-out：room meta.json 加 `disable_quest_mirror: true` → reducer 跳過鏡像
- 個別 op 有 `--arg quiet=true` → 強制不鏡像（測試 / 自動化大批 ops 用）
- 不做使用者可調的「哪些 event 要鏡像」granular config — over-engineer

### 5. Edge cases

- **房間沒 messages.jsonl**：理論不可能（Quest 房規矩 一房一 quest，一定先 createroom 才有 events.jsonl），但 defensive code 加 if-not-exists skip
- **idempotency dedup 跳過 event**：reducer 看到 idempotent skip → 不鏡像（避免重發 cmd 多寫 chat 訊息）
- **task_progress 沒 summary**：跳過鏡像（不然每次 lease 展期都吵）
- **長 reason / summary 截斷**：> 80 字截 + … 後綴；完整內容仍在 events.jsonl
- **brainstorm 房同時是 quest 房**（少見，但 brainstorm 結論轉 quest 後用同房）：鏡像會跟對話交錯 — meta.event_type 區分 / IMGUI 可選擇性過濾

## 整合考量

### 跟 Discord-inspired 的關係
- Discord Top 5 的 A2「頭像連續去重」在 system messages 上要特別處理（不該被當 continuation 壓縮）
- A1 日期分隔線正常套用
- 看 sender_id 開頭 `_` → 用特殊樣式（淡色 / 較小字）

### 跟 events_since 的重疊
- events_since 已給 delta timeline，但是「拉式」（agent 主動跑）
- chat mirror 是「推式」（自動寫進對話）
- 兩者互補不衝突 — agent 入場仍跑 events_since 看 delta，但已聊天活躍時即時看到 task 動態

### 跟 PromptQueue 的關係
- `agent-prompt-queue` 房目前每筆 queued task 都會留下 task_create/claim/done event
- 鏡像後 messages.jsonl 也會有「🆕 queued / 🔒 drained / ✅ done」三筆
- 預期效果：Tim 進這房直接看到 PromptQueue 進度時間線，不必跑 qstatus.py
- 副產品 — qstatus.py 可改用 messages.jsonl tail（更輕）
