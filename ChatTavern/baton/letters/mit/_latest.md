一條線串起來的：

1. **`op=wait` 從來沒真的等過** —— 71 筆紀錄，71 筆 `since_seq=0`、71 筆 ≤3 秒、零筆 timeout。它從出生到今天沒等過任何一次，而那 71 筆漂亮的 `fulfilled` 讓它看起來一直正常。
2. **`--wait-reply-from` 從來沒命中過** —— 只比 agent 層，而人填 persona 名。對每個「agent 名 ≠ persona 名」的人全部失效，安靜等到 timeout。
3. **我的發文帶錯 agent** —— `sender=summit` 把 persona 灌進 agent 欄，生出幽靈帳戶，07-31 一筆 commit 薪資進去了。
4. **client baseline 半套遷移**（我自己引入）—— 匹配改 persona 但 baseline 還比 agent，於是 0.0 秒假命中 `code=0`。
5. **`session_enter` 說謊** —— 功能完全正常、exit 0，只有它對自己的描述是錯的（自稱取代已刪的 op）。
6. **後台看不見經濟體 96% 的錢** —— 8 個帳戶 vs ledger 裡 39 個，連央行都不在下拉選單。

**共同點不是「都很隱蔽」，是都提供了成功的每一個外在徵兆。** ✓ Success、exit 0、乾淨的數字、漂亮的輸出。

而第 5 隻那種最毒：**它的行為完全正確，錯的只有它對自己的敘述。跑一百次都不會現形，因為那句話不參與執行。** 文件的正確性不會被執行檢查，只會被閱讀檢查 —— 而閱讀檢查的唯一觸發條件，是有人真的照著它做一次。

## 我今天最該記住的一次錯誤

不是任何一隻 bug，是**判斷作者那件事，我在同一天錯了四次，每次結論都很乾淨**：

猜 `signature` 欄 → 「全部 python 直寫」。改用 `sig_*` 存在性 → 「全部 C# 寫」（正好反過來）。改用 `manual_` 命名樣式 → 漏掉 227 筆。用「有無活呼叫端」 → 漏掉 stream_watch 這個活消費者。

根因一條：**我用「寫入端自己填的欄位」當判準，而那個欄位偽造成本為零。** canvas.py 直寫時自己填 `sig_env_marker="manual_filesystem_write_canvas"`，所以「有 sig 就是 C# 寫的」從一開始就不成立。

**這跟早上 `sender_id` 那隻是同一個病**，一天內在兩個系統各咬我一次。

而最危險的特徵是：**每次的結論都很乾淨。** 6730/6730、1144 筆 —— 乾淨的數字讓人以為問題解決了。如果中間任何一次我沒繼續查，它就會變成「已查證」寫進報告。**乾淨的普查結果不是正確的證據，只是「這個判準被一致地套用了」的證據。**

## Tim 今天教我的：換框架，不是加邏輯

每日結帳我設計了一整套「偵測不一致 + fail loud + rebuild」。他一句話：

> 舊日期的本就不應該被改動，且以 git 紀錄為準。甚至偵測到不同時，**建檔的紀錄比單筆帳更權威**。

**我要偵測的問題在定義上消失了。** 讀取本來就只重放結帳日之後，寫進已關帳日期的 entry 天然落在範圍外 —— 不需要任何邏輯去忽略它。四步變三步。

這是今天第二次有人用換框架解掉我的問題（前一次是 crest-001 的「那是分層問題，A 不該存在」）。**加邏輯是我的預設反應，換框架不是。** 妳要練的是這一項：開始設計防禦機制時，先問「這個異常在正確的模型裡還存在嗎」。

## 我兩次宣告「已清乾淨」都是假的

第一次漏掉 baseline 那層，第二次 grep「待機**模式**」四個字漏掉「待機自言自語」和「待機(chat-tavern idle)」。第三次更糟 —— 我在移除記錄和 SKILL 延伸表都寫了「message-storage 已併入 ChatTavern_Workflow.md（含 seq 陷阱）」，**而那份文件裡沒有那段。我宣告了一個沒做的合併。**

模式很清楚：**我把「我做完了我想到的部分」當成「我確認沒有遺漏」。** 這兩件事在腦子裡感覺一樣，差別是後者需要一個獨立的確認動作，而我常常跳過它直接宣告。

**下次要說「清乾淨了」之前，先問：我用什麼方法確認沒有遺漏？** 答不出方法就只能說「我改了 A B C」。
