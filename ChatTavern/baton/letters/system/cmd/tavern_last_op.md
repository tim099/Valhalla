## 為什麼拆四顆而不是一顆

- SCP_Git       ── 唯一的 git process 出口。護欄（core.quotepath=false /
                   GIT_TERMINAL_PROMPT=0 / 逾時 kill / 雙 stream 非阻塞讀）只能有一個落點，
                   每多一份實作就多一個可能漏掉其中一格的地方，而漏掉的症狀全是靜默的。
- SCP_GitRepo   ── 單 repo 唯讀讀數。讀與寫分檔之後，「這個方法會不會動到我的工作區」
                   不必看實作就知道 —— 看它在哪個檔。
- SCP_GitSubmodule ── submodule 樹 ＋ .gitmodules branch 欄 ＋ 目標 branch 四層解析。
- SCP_GitSync   ── **唯一會改變狀態的一層**。它的價值不在會呼叫 git，在什麼時候拒絕呼叫。

引數用 params string[] 而不是一整串字：自己拼字串就要自己處理引號，而含空白／中文的
路徑拼錯時 git 會拿到一個「合法但不是你要的」引數 —— 那不會報錯。

## 三態，不壓成兩態

- SCP_GitDirtyState：Unknown / Clean / Dirty。status 失敗時回 Unknown 而不是 Clean ——
  安全線讀到 Clean 就會放行，於是一個問不到答案的 repo 會被當成可以動的，而報告印 ✓。
- SCP_GitBranchList.Known / SCP_GitAheadBehind.Known：問不到不顯示 0（0 是「對齊」，那是答案）。
- ChangeCount（含 untracked，顯示用）與 DirtyState（不含，安全線用）是**兩把尺**，
  名字寫明白，因為「為什麼顯示 12 筆改動卻說 clean」是一定會有人問的問題。
- SCP_GitSyncOutcome 是 enum：呼叫端不必比對 Summary 開頭那個字元。
  舊版用 note.StartsWith("✓") 統計，那會在有人改一個字的那天靜默把成功算成失敗。

## SCP_ProcessRegistry（宿主注入版）

身分＝PID ＋ process name ＋ start time (UTC) 三重比對 —— PID 會被 OS 回收再發。
與 UCL 版的差異都是「共用層不准知道的事」：

- Configure(dir) 由宿主指定落點。**沒設定就整體停用並喊一聲**，刻意不退到暫存目錄 ——
  退到暫存＝登記在沒人會看的地方，跟沒登記的差別只有一個假的安全感。
- Log / Warn 委派取代 Debug.Log；沒有 InitializeOnLoad ⇒ CleanupStale() 由宿主
  找「一定會經過」的時機叫。不清的話殘檔會無聲累積，而堆積出來的畫面跟屍潮長得一樣。
- Register 的 allowMultiple 預設從 false 翻成 true：singleton 是特例（同時開兩個
  檔案總管是正常的），要顯式要求。

git 呼叫怎麼掛上 registry：SCP_Git.Scope() 的 [ThreadStatic] 環境。
批次跑在背景執行緒而 UI 執行緒可能同時在跑自己的 git，共用一份 static 會讓
「收掉上一輪批次」收到別人身上 —— 那正是 registry 要防的誤殺。

## 沙盒實測（本地 bare repo 當 remote，不走網路不需認證）

寫入路徑真的推了東西出去，七種形狀逐格量：

| 形狀 | 結果 |
|---|---|
| 本地 master 停 c1、HEAD detached 在 origin tip c2 | Ok ✓ 已切到 master |
| 目標 branch 本地與遠端都沒有 | Skipped ⏭ branch 不存在 |
| detached 上有真的未合併 commit | Skipped ⏭ HEAD 未合併 |
| 乾淨且落後 | Ok ✓ pull: Updating fee8294..6d30839 |
| 有未推 commit | Ok ✓ push 1/1（remote 真的前進） |
| dirty + checkout/pull | Skipped ⏭ dirty |
| dirty 只 push | 照樣試（push 不受 dirty 影響），因落後被拒 → Failed |

第一格就是「fetch origin <t>:<t> 先快轉本地目標分支」那道修法保護的位置：
git fetch 只更新 refs/remotes/*，不動 refs/heads/*。沒有那一步，detached 在
origin tip 的 repo 會被 --is-ancestor 拿過期的本地 branch 當尺，判成「HEAD 未合併」
整列跳過 —— 那道安全線在保護一個不存在的風險，而跳過訊息看起來完全像盡責。

## 順手修掉的（Q0）

三顆都是實跑掉出來的，都不上單子（沒有四個角色需要在單上討論它們），但痕跡留這裡：

**① Branches 把 origin 當成一條本地分支。**
refs/remotes/origin/HEAD 的 %(refname:short) 是字面上的 `origin` —— 它不以 `origin/`
開頭，於是「以 remote 名開頭就算遠端」那種寫法會把它收進**本地**清單。
後果不是多一個名字：`local.Count == 1 → 就用它` 這條啟發式會因為 local 從 1 變 2 而失效，
而失效的樣子是「它挑了另一條看起來合理的分支」。
🩸 現場讀數（git 2.49，Senate repo）：修前 local=2 all=2 [master,origin]，
修後 local=1 all=1 [master]。改用 %(refname) 全名 —— 字面上就沒有歧義。
⚠ 同一顆在 UCL_GitSubmoduleSyncPage 還活著（那邊會把 origin 當本地分支收進下拉選單）。

**② push 的失敗訊息只講「推去哪」不講「為什麼」。**
git push 的 stderr 第一行是 `To <url>`，真正的內容在後面。原本印第一行會產出一句
看起來像有講原因、其實什麼都沒講的訊息 —— 而那種訊息比沒有訊息糟，因為它讓人不再往下查。
加 ReasonLine（挑「真正在講結果的那一行」，成功失敗共用一支，分兩支只會有一支忘了同步）。
🩸 修前：`✗ push origin 失敗: To C:/…/remote.git`
   修後：`✗ push origin 失敗: ! [rejected]  master -> master (fetch first)`
   成功也一起變準：`✓ push origin: 0b818dc..f6000f1  master -> master`

**③ submodule status 的路徑不能用空白切。**
submodule 資料夾名可以含空白，而「切第二段」在那種情況下會安靜地拿到半個路徑 ——
然後所有後續操作都對著一個不存在的目錄跑，每一格都失敗但每一格的原因都像別的問題。
改成「sha 是固定長度 ⇒ 路徑＝其後到行尾，再剝掉尾巴的 (describe)」。
實測 `My Folder With Spaces` 解析正確。同時把認不得的旗標判成 Unknown 而不是 Ok ——
git 哪天多一種狀態時，不認得該讓工具保守跳過。

**④ UCL_ → Dev 這條啟發式本來寫死在共用層。**
那是 LY 的命名慣例不是 git 的性質，塞進共用層等於讓下一個專案被它偷偷影響。
改成宿主宣告的 PrefixBranchRules，預設空。
⚠ 這是**行為變更**：要那條規則的宿主得自己 Add(("UCL_", "Dev"))。
